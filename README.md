# Serverless Order API: Plain Java, AWS Lambda, and API Gateway

## Project Overview

This repository contains a small order-management application developed with ordinary Java classes and Maven. Its order operations are deployed as AWS Lambda functions and exposed to HTTP clients through an Amazon API Gateway REST API.

The implementation deliberately separates the Java order operations from the HTTP interface. The Java code defines an `Order` model, validates order input, and provides methods for creating and retrieving orders. API Gateway defines the routes and translates HTTP requests into JSON events that the Lambda Java runtime can pass to those methods. API Gateway also maps Lambda results and errors to HTTP responses.

The current API exposes three operations:

- `POST /orders` creates an order.
- `GET /orders/{id}` retrieves one order by its identifier.
- `GET /orders?customerId={customerId}` retrieves the orders associated with a customer.

> The Java service currently keeps sample and created orders in a static, in-memory list. 

## API Design

The API uses `Order` as its principal resource. An order contains an identifier generated by the application, a customer identifier, a product description, and a positive quantity.

### Create-order request

The client provides the customer, product, and quantity. It does not provide the order identifier.

```json
{
  "customerId": "CUST-42",
  "product": "MacBook Air",
  "quantity": 1
}
```

### Order response

A successful creation or retrieval returns an order representation. The `id` is generated by the Java application.

```json
{
  "id": "<server-generated-uuid>",
  "customerId": "CUST-42",
  "product": "MacBook Air",
  "quantity": 1
}
```

### Error response

Errors use a stable machine-readable code and a human-readable message.

```json
{
  "error": "ORDER_NOT_FOUND",
  "message": "Order not found"
}
```

The current not-found message is generic: the service returns `Order not found` rather than including the requested identifier. The response should not expose a Java stack trace or other internal runtime details.

### API design questions

**1. What are the resources in the API?**

The primary resource is an order. `/orders` identifies the collection of orders, while `/orders/{id}` identifies one order in that collection. The customer-order search is a filtered view of the order collection; this API does not expose a separate customer resource.

**2. Why use `/orders/{id}` to retrieve an order?**

The order identifier uniquely identifies one resource. Placing it in the path expresses that the request targets a particular order, which is the conventional REST representation of an individual resource.

**3. Why is `customerId` a query parameter?**

`customerId` filters the order collection rather than identifying an order. Therefore, `GET /orders?customerId=CUST-42` requests the collection entries matching a criterion. The path parameter in `/orders/{id}`, by contrast, selects one particular order.

**4. What should a successful `POST /orders` return?**

The API returns `201 Created` and the created order representation, including the server-generated identifier.

**5. What should the API return when an order does not exist?**

`GET /orders/{id}` returns `404 Not Found` with an error body such as `{"error":"ORDER_NOT_FOUND","message":"Order not found"}`. 

**6. What information should an error response contain?**

An error response should contain a stable error code that clients can interpret and a concise message that explains the failure. For example, `ORDER_NOT_FOUND` identifies the failure category, while `Order not found` describes it. It should not expose implementation-specific stack traces.

## Implement the Application in Plain Java

The project contains the following source files:
```text
orders-api/
├── pom.xml
└── src/
    ├── main/
    │   └── java/eci/arem/
    │       ├── Order.java
    │       ├── OrderService.java
    │       ├── dto/
    │       │   ├── CreateOrder.java
    │       │   └── OrderMapper.java
    │       └── exception/
    │           ├── HttpStatusCode.java
    │           ├── OrderErrorCode.java
    │           └── OrderException.java
    └── test/
        └── java/eci/arem/
            └── OrderServiceTest.java
```

`Order.java` defines the order record and its identifier-based equality. Its convenience constructor generates a UUID when a new order is created. `dto/CreateOrder.java` represents the create-order input, checks that the customer and product are not null or blank, requires a positive quantity, and trims the text values. `dto/OrderMapper.java` converts a validated `CreateOrder` record into an `Order`.

`OrderService.java` provides the static create, lookup-by-ID, and lookup-by-customer operations. It initializes sample orders, including the fixed `TEST-ORDER-001` record used in read-function demonstrations, and stores orders in a static `ArrayList`. `exception/OrderException.java`, `OrderErrorCode.java`, and `HttpStatusCode.java` define the application’s error types, messages, and associated numeric HTTP status values. `OrderServiceTest.java` contains the JUnit tests for these classes.

### Checkpoint

**Can the application functionality be tested without AWS?**

Yes. The JUnit tests instantiate the Java records and call `OrderService` directly. AWS is not required to exercise the validation, mapping, creation, or lookup logic. AWS is required only for verifying the deployed Lambda and API Gateway integration.

**Does the application require a web server?**

No. The Java project contains no HTTP server. The order methods can be called directly in tests and are invoked by the Lambda Java runtime after deployment. API Gateway supplies the public HTTP endpoint in the deployed system.

**Does it require Spring Boot?**

No. The source is plain Java and the POM contains no Spring Boot dependency. The application does not depend on a Spring application context or Spring web controller.

**What does the generated JAR contain?**

It contains the compiled application classes and Maven archive metadata. The JUnit test dependency is test-scoped and is not part of the application runtime. The JAR does not contain a web server or a `main` method. AWS Lambda selects the target class and method through the function’s handler setting.

**Which parts of the application currently know about HTTP?**

API Gateway knows about HTTP methods, paths, query parameters, request/response transformations, and public status codes. In the Java project, `HttpStatusCode` and `OrderErrorCode` also refer to HTTP status values. `OrderService` itself does not parse an HTTP request or construct an HTTP response. Thus, HTTP is mostly outside the service operations, but the exception/error-code layer is not fully transport-independent.

### Investigation: JSON conversion in the Java Lambda runtime

A Lambda invocation arrives as a JSON event. The Java Lambda runtime uses the handler method’s declared input type to deserialize that JSON into a Java value. It invokes the configured method and serializes the returned Java value to JSON. AWS documents Java record event types for Java Lambda handlers and supports method-handler names in the form `<package>.<Class>::<method>` when an interface-based handler is not used. This project targets Java 25, and its `CreateOrder` record is used as the input type for the create-order handler.

In this repository, `addOrder(CreateOrder request)` receives an object with `customerId`, `product`, and `quantity`. Deserialization constructs the `CreateOrder` record; its compact constructor validates and trims the values. `OrderMapper` then creates an `Order`, and the method returns that record. The runtime serializes the returned record into a JSON object. The read methods return either one `Order` or a `List<Order>`, which the runtime serializes as a JSON object or array, respectively.

## HTTP Semantics and Error Mapping

A JSON response alone is not sufficient to define the HTTP contract. The current integration uses API Gateway Method Responses and Integration Responses to select status codes and format error bodies. With a Lambda custom integration, API Gateway must map Lambda errors to HTTP errors; otherwise, Lambda function errors can be returned with an inappropriate default `200 OK` response.[4]

The API behavior evidenced in the repository is summarized below.

| Request outcome | HTTP response | Body or behavior |
|---|---:|---|
| Create an order successfully | `201 Created` | The created `Order`, including its generated ID |
| Retrieve an existing order | `200 OK` | One `Order` object |
| Retrieve a missing order | `404 Not Found` | `ORDER_NOT_FOUND` with `Order not found` |
| Search for a customer with orders | `200 OK` | A JSON array of matching orders |
| Search with no matching orders | `200 OK` | An empty JSON array, as returned by `OrderService` |
| Missing or blank `customerId` | `400 Bad Request` | `BLANK_NULL` with `Value cannot be null or blank` |
| Invalid create-order body | `400 Bad Request` | `INVALID_INPUT` with a generic validation message |

For `GET /orders/{id}`, the Java service throws `OrderException` with the message `Order not found` when no item matches. API Gateway selects the corresponding integration response using the configured Lambda error regular expression and maps the response body to the public error representation. For an absent or blank customer identifier, the service throws the `BLANK_NULL` error; the configured integration response maps that message to `400 Bad Request`.

The create-order route uses a general `400` mapping, whereas the read routes use more specific mappings, because the errors arise at different points in the request flow. For `GET /orders/{id}`, the JSON string is deserialized successfully and `OrderService.getOrderById` runs. If the order does not exist, that method throws the known `OrderException` message `Order not found`; API Gateway can match that stable message with `.*Order not found.*` and return `404 ORDER_NOT_FOUND`. For `GET /orders?customerId=...`, a missing or blank string also reaches `OrderService`; it throws the known `Value cannot be null or blank` message, which API Gateway maps to `400 BLANK_NULL`.

`POST /orders` follows a different path. Before `OrderService.addOrder` can run, the Lambda Java runtime must deserialize the request body into the `CreateOrder` record. The record’s compact constructor performs validation during that deserialization. If validation throws, the failure occurs before the handler method executes, so the method cannot catch it and translate it into a stable operation-specific response. The current API Gateway integration therefore uses the catch-all error pattern `.*` to normalize invalid POST bodies as `400 INVALID_INPUT` with a general message. The saved Postman captures show this response for missing fields, blank values, and a negative quantity.

This catch-all is a deliberate simplification for the laboratory. It can also classify an unexpected Lambda error as `400`, so a production implementation should distinguish known input-validation failures from unhandled server errors and map those to suitable `5xx` responses.

### Checkpoint API Gateway Responsibilities

In the current non-proxy design, API Gateway is responsible for the HTTP-facing contract and its transformation rules. Specifically, API Gateway:

1. Routes `POST /orders`, `GET /orders/{id}`, and `GET /orders?customerId=...` to their corresponding Lambda functions.
2. Extracts the path identifier and customer query value from the HTTP request.
3. Transforms the path and query values into JSON string events and passes the create-order JSON body as an object.
4. Invokes the configured Lambda function and receives its JSON output or function error.
5. Defines the successful method-response status codes, including `200` and `201`.
6. Selects error responses and maps them to `400` or `404` with the API’s JSON error format.
7. Exposes the API through the deployed stage URL.

### Advantages of this distribution

The Java order methods do not need to parse the full API Gateway event or build an HTTP response envelope. This keeps the central order operations directly testable with JUnit and avoids adding a web framework or standalone web server. API Gateway can expose the HTTP contract while the Java methods continue to work with values such as `String`, `CreateOrder`, `Order`, and `List<Order>`.

The configuration also makes the mapping between a public HTTP request and a particular Java operation explicit. A client-facing `404` or `400` can be demonstrated without adding an HTTP controller to the plain Java project.

### Disadvantages and trade-offs

Part of the API behavior is configured outside the Java repository. Request templates, error regular expressions, Method Responses, Integration Responses, and the deployed stage must remain consistent with the Java method signatures and exception messages. A change to an error message can break a regular-expression mapping even when the Java service still compiles. The screenshots provide evidence of console configuration, but the repository currently does not contain an infrastructure-as-code definition that can recreate the full API Gateway deployment automatically.

Responsibility is also split across layers. `OrderErrorCode` stores numeric HTTP status values in Java, while API Gateway separately maps Lambda errors to the actual HTTP status and hard-codes the public error code in response templates. This duplication can drift. A later architectural refinement could make the Java error model transport-neutral and define the HTTP mapping in one explicit adapter or API deployment specification.

Finally, API Gateway mappings do not solve the application’s in-memory data limitation. The current implementation does not provide durable order storage or reliable sharing of newly created orders across the three separate Lambda functions.
